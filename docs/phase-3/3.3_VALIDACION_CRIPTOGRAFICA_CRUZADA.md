## 3 Núcleo compartido en Rust

### 3.3 Validación criptográfica cruzada

**Alcance:** seleccionar una primitiva ampliamente revisada y contrastar vectores públicos en implementaciones diferentes. **No** se activó cifrado de archivos de usuario, SQLite cifrada, almacenamiento de claves, E2EE, rotación ni recuperación: esas son obligaciones posteriores de las etapas 4 y 6.

**Algoritmo y bibliotecas:** AES-256-GCM AEAD (clave 32 bytes, nonce 12 bytes, etiqueta 16 bytes); RustCrypto `aes-gcm =0.10.3` para Rust y `cryptography==44.0.2` (OpenSSL) como implementación Python independiente. Son bibliotecas establecidas, **no se afirma auditoría externa de SMART UNI ni certificación FIPS**. La elección deberá revisarse periódicamente.

**Vectores públicos:** `core/rust/test-vectors/aes256gcm.json` incluye los dos vectores de AES-256-GCM con clave y nonce cero, plaintext vacío y bloque de 16 bytes cero. Fuente pública contrastable: [BoringSSL / vectores GCM de NIST](https://boringssl.googlesource.com/boringssl/+/e8c862cf1421/crypto/cipher/test/aes_256_gcm_tests.txt).
- Vector vacío: etiqueta `530f8afbc74536b9a963b4f1c4cb738b`.
- Vector de un bloque: ciphertext `cea7403d4d606b6e074ec5d3baf39d18` y etiqueta `d0d1c8a799996bf0265b98b5d48ab919`.
- Claves y nonces cero se usan **solo** en tests, nunca para cifrar datos del producto.

**Pruebas reales:** Rust comprueba resultados exactos, roundtrip usando nonce aleatorio de `OsRng`, variación de nonce y rechazo de etiquetas o AAD alterados. `scripts/check_crypto_vectors.py` usa OpenSSL mediante cryptography para reproducir ambos resultados y confirmar rechazo de modificación. El puente FFI y el consumidor C++ invocan la KAT Rust. Los mismos tests corren en Windows y Ubuntu; la compilación arm64 Android se comprueba sin ejecución.

**Requisitos de seguridad pendientes:** elección y derivación de claves por dispositivo, no reutilización global de nonce+clave, rotación, almacenamiento protegido en Windows/Linux/Android, límites de tamaño, zeroization, definición de contenedor/versionado autenticado, backup, recuperación y pruebas de interoperabilidad de contenido entre dispositivos reales. `seal_random` acepta una clave del llamador y devuelve nonce/ciphertext+tag, pero **no** se integra en persistencia ni constituye por sí solo un protocolo completo.

**Aceptar 3.3:** las KAT y la prueba independiente deben aprobar en ambos SO; compilación de biblioteca Android ARM64 sin fallos; registrar resultados reales en acta de cierre. No confundir pruebas de algoritmos con pruebas E2EE entre dispositivos.
