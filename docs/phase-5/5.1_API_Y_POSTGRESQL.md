## 5 Backend, identidad y autorización

### 5.1 API y PostgreSQL

**Implementación verificada:** `services/api/app/main.py` expone FastAPI 0.162.0 y usa SQLAlchemy 2.0.51 + psycopg3 contra PostgreSQL. No existe fallback SQLite. El código PostgreSQL es del servicio, **no** de los clientes desktop/Android.

**Esquema versionado:** `services/api/migrations/versions/0001_identity_notes.py` (Alembic) crea identidades (issuer+subject únicos), notas (FK owner_id) y hashes de revocación de tokens. Migración hacia arriba, rollback y re-aplicación comprobadas con PostgreSQL 16 en GitHub Actions. Los campos enviados por cliente pasan por esquemas Pydantic; las consultas SQLAlchemy parametrizan filtros e IDs, sin concatenar SQL. El servidor asigna propietarios por JWT verificado y cuenta PostgreSQL, ignorando actor_ref externo.

**Rutas efectivas:** healthz liveness; me; notas GET/POST/GET por UUID/PUT/DELETE (propietario requerido); admin/metrics solo rol de BD; sessions/revoke para bearer de esa API. Notas actuales aún quedan en texto claro en PostgreSQL, SOLO se utilizan datos sintéticos hasta crear protocolo E2EE en etapa 6.

**Verificación:** 14 pruebas de integración con PostgreSQL 16 real y firmas RSA genuinas; emisor/audiencia/expiry rechazados, SQL injection tratado como datos, 404 cross-owner y rol cliente ignorado, migraciones reversibles. [Actions #42226125117](https://github.com/Gh0stDeveloper/smart-uni/actions/runs/42226125117). Los secretos reales del IdP/DB NO se han conectado.

**Criterios satisfechos dentro del laboratorio:** API y migraciones funcionales, modelo de datos versionado, entradas validadas, consultas parametrizadas, permisos por propietario probados. **No satisfechos en producción:** despliegue HTTPS, política RLS con rol Postgres restringido, pool/retención, backup, cifrado E2EE, rate limiting/SBOM, conexión IdP externa.
