## 2 Contratos y sistema de diseño

### 2.2 Contratos compartidos

**Ámbito:** especificar formatos entre futuros clientes y servicios; no crear red, backend, sincronización, cifrado ni migración de datos.

**Fuente versionada:** [`packages/contracts/v1/registry.json`](../../packages/contracts/v1/registry.json) y [README](../../packages/contracts/README.md). Versión del contrato `1.0.0`; almacenamiento local actual `version: 1`. Los tipos de entrada están descritos por JSON Schema Draft 2020-12.

| Elemento | Archivo | Regla |
|---|---|---|
| Operaciones | `envelope.schema.json` | Enum de diez operaciones documentadas; `operation_id` UUID hex32, `occurred_at` UTC, `payload` JSON |
| Errores | `error.schema.json` | Siete códigos estables con mensaje y detalles opcionales; no exponer secretos |
| Persistencia antigua | `legacy-json.schema.json` | Compatibilidad para JSON v1 sin reescribir bases existentes |
| Identificadores y versiones | `registry.json` | ID local de entidad hex32, correo de referencia no autenticado, control de versión |
| Casos sintéticos | `examples/` | Operación, error y base legada válidos; versión futura rechazada |

El mensaje futuro aporta `actor_ref` **no fiable** desde el cliente. Toda API debe identificar al usuario a partir de sesión/OIDC validada y aplicar autorización por recurso. Ninguna prueba aquí demuestra que ya exista servidor o permisos remotos.

**Pruebas reproducibles:** `python scripts/check_contracts.py` con `jsonschema==4.23.0`; verifica validez Draft 2020-12, fixtures reales sintéticos, enums del registro y rechazos de versiones/códigos/IDs. `apps/desktop/tests/test_phase2_contracts.py` asegura coherencia del repositorio y conservación del JSON antiguo sin dependencia de runtime.

- [x] Esquemas, IDs, operaciones y códigos versionados y documentados.
- [x] Fixtures positivos/negativos y validador técnico incorporados.
- [ ] Github Actions y regresión Windows/Linux en verde en el commit de cierre.
