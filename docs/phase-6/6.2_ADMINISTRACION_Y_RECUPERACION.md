## 6 Cifrado y gestión de claves

### 6.2 Administración y recuperación

**Manejo de claves:** `apps/desktop/smart_uni/secure_storage.py` custodia la clave SQLCipher de 32 bytes en un backend keyring permitido por sistema operativo; `secure_files.py` genera OTRA clave de contenido aleatoria de 32 bytes por usuario en el mismo almacén. Al faltar una clave existente, se **rechaza** la lectura o se solicita recuperación explícita. No se guarda passphrase en repositorio/DB/UI; no existe recuperación por servidor.

**Copia offline de recuperación:** `core/rust/src/recovery.rs` implementa Argon2id v0x13 (64 MiB, 3 pasadas, 1 lane, salida 32 bytes), sal de 16 bytes aleatorios, AES-256-GCM con nonce de 12 bytes y tag de 16 bytes. Paquete fijo `SURECV01`:
- Magic: 8 bytes.
- Salt Argon2id: 16 bytes.
- Nonce AES-GCM: 12 bytes.
- Clave de 32 bytes cifrada + tag: 48 bytes.
- Total: **84 bytes**; magic/salt/nonce son el AAD. No se guardan la clave ni la frase en texto claro en esta copia.
- Frase aceptada: 16–512 bytes UTF-8. Esto NO prueba que tenga alta entropía: el usuario debe elegir una frase aleatoria robusta. A diferencia de HPKE, un atacante con el paquete puede hacer intentos offline de fuerza bruta; proteger y respaldar por separado paquete y frase.

**Recuperación independiente de dos claves:** `apps/desktop/smart_uni/key_recovery.py` exporta y restaura clave **SQLCipher**. Verifica PRAGMA cipher_version, integrity_check y existencia de snapshot de la base ANTES de reinstalarla en keyring. `SecureMaterialStore.export_recovery / restore_content_key` respalda la clave **de materiales** y valida que pueda descifrar un archivo existente antes de aceptarla. Para recuperar una instalación se necesitan: base SQLCipher íntegra + paquete/contraseña de su clave, archivos `.sun1` + paquete/contraseña de contenido. El JSON heredado no se borra automáticamente; el UI de recuperación todavía no existe. Copias recuperables en soporte externo y su custodia quedan a cargo del operador/usuario.

**HPKE por dispositivo:** `core/rust/src/devices.rs` implementa HPKE RFC 9180 modo Base usando X25519/HKDF-SHA256/AES-256-GCM; envuelve la clave de contenido a una clave pública de cada dispositivo. El módulo Rust incluye `DeviceRoster` de laboratorio con altas, bajas y epochs: `revoke_and_rotate` cambia epoch y genera una nueva clave aleatoria para destinatarios activos. El modo Base **NO autentica quién envía**. Un dispositivo retirado conserva TODO lo que ya haya descifrado o la clave antigua que recibió. Para proteger nuevos contenidos hace falta cifrarlos con la **nueva clave**, reencriptar material antiguo si se desea restringirlo, publicar/validar la clave pública y confirmar enrolamiento por un canal autenticado.

**No realizado y explícitamente pendiente:** el roster es **en memoria**, no persiste ni está integrado a OIDC/API/Android/desktop; no existen pruebas de posesión de la clave privada, enrolamiento de dispositivos aprobado, alerta al usuario, revocación firmada por servidor, sincronización/re-wrap de todas las claves, rotación automática de DB ni controles hardware Keystore/DPAPI/SecretService probados en equipos físicos. La biblioteca HPKE Rust declara no haber sido auditada externamente; requiere revisión antes de producción. Ver P15/P25/P30/P37/P38/P41.

**Pruebas:** recuperación de claves con paquete, contraseña equivocada, manipulación y paquete truncado; Python Argon2-cffi independiente ↔ Rust; copia DB cifrada recuperada en SQLCipher; envoltura HPKE a dos destinatarios, revocación/epoch, clave nueva y acceso histórico irreversible. No se ha enviado ninguna clave privada por HTTP.
