# 8.3 Rust y Android Keystore — segunda integración

## Nuevo almacenamiento cifrado

Android enlaza `smartuni-core` Rust estático vía C++/JNI para ARM64 y x86_64. La DEK aleatoria AES-256 se genera localmente y se envuelve con una clave del proveedor AndroidKeyStore en `local_key.wrap`, nunca se persiste sin envolver. La misma DEK se usa en contextos AAD distintos para:

- `local_note.sun1`: apunte cifrado de primera iteración, preservado para migración conservadora.
- `local_vault.sun1`: bóveda cifrada que incluye apuntes, tareas, eventos y metadata de materiales; esquema 1, límite 512 KiB.
- `encrypted_materials/<uuid>.sun1`: contenido Rust AES-GCM por archivo con AAD vinculado al identificador aleatorio, máximo 8 MiB.

La pérdida de `local_key.wrap` no produce una nueva clave cuando ya existe bóveda, apunte o material cifrado: la carga **falla cerrada** en vez de sobrescribir los datos con una clave distinta. Backups Android permanecen desactivados para evitar restauraciones de ciphertext sin Keystore. La importación no elimina el archivo fuente del proveedor y limita el tamaño antes de escribir contenido privado.

## Pruebas añadidas

`NativeCryptoInstrumentedTest` incluye pruebas para roundtrip Rust, corrupción/tag, AAD incorrecto, rechazo de URLs inseguras, alta y reapertura de datos multi-registro en `LocalVault`, corrupción en disco con recuperación del original del test, llamada JNI sin token válido y existencia de clave AndroidKeyStore. Las pruebas están definidas en el repositorio pero **su aprobación depende de un emulador y de dispositivos reales**.

El workflow incorpora límites `timeout` al diagnóstico ADB para evitar trabajos que nunca finalizan cuando el emulador queda offline. Ni un build correcto ni una prueba x86_64 demuestra hardware TEE/StrongBox.

## Impedimentos para cierre
