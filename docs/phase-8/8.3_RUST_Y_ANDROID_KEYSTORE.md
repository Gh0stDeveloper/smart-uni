# 8.3 Rust y Android Keystore

## Implementado

Gradle/CMake exige Rust `staticlib` por ABI (arm64-v8a y x86_64); enlaza `smartuni_seal_record_v1` y `smartuni_open_record_v1` con C++ JNI. Contenedor `SUAEAD01`: AES-256-GCM, AAD específico del apunte local; se reutiliza exactamente la ABI de escritorio, no un cifrado Android casero. `KeyVault.java` crea una DEK aleatoria de 256 bits y la envuelve en AES-GCM **con clave AndroidKeyStore**, nunca persiste la DEK en claro. `AtomicFile` protege la sustitución de nota y clave envuelta ante interrupción de escritura; si el paquete se corrompe o Keystore desaparece, aborta.

El manifiesto deshabilita backups y tráfico claro; se usa almacenamiento privado. No hay contraseña maestra universal ni un modo plaintext de emergencia.

## Pruebas y distribución

- Test de instrumentación: ABI 1 y KAT Rust, roundtrip real, corrupción y contexto diferente, lectura tras recargar de disco usando Keystore, rechazo de origen HTTP.
- CI: compilación de `libsmartuni_core.a` Android por ABI, Gradle APK debug y release / AAB release sin firma comercial, prueba automatizada en emulador x86_64.
- APK debug usa una firma de depuración no apta para distribución. Para APK/AAB release firmados se requieren credenciales de firma externas inyectadas; CI **no almacena** llaves comerciales.

## Bloqueos

- Android Keystore no significa StrongBox/TEE demostrado; faltan instrumentación de capacidades, atestación y política de hardware.
- No hay SQLite/SQLCipher de múltiples entidades, vault de cuenta ni claves E2EE/HPKE enroladas para sincronización compartida.
- Falta firma comercial y verificación de certificados, pruebas en dispositivo físico/reinicio/upgrade, backup y recuperación, y audit/Play testing. No se deben cargar datos de estudiantes reales.

**Resultado:** integración criptográfica Android de laboratorio; cierre productivo pendiente. Ver [acta](8_CIERRE_Y_EVIDENCIAS.md).
