# 8.2 Comunicación C++/JNI — segunda integración

## Puente nativo y endpoints

Se conserva el adaptador anterior de diagnóstico `GET /healthz`. El nuevo `NativeBridge.apiRequest` delega la elección de rutas a `bridge.cpp` C++ y utiliza el TLS oficial de Android mediante `NativeHttpTls` invocado desde JNI:

| Operación | Método y ruta fija en C++ | Estado |
|---|---|---|
| 0 | GET /api/v1/me | Código de request; falta sesión real |
| 1 | GET /api/v1/sync/pull?cursor=...&limit=10 | Código de request; falta procesamiento E2EE de lotes |
| 2 | POST /api/v1/sync/push | Código de request; falta cola/ACK local |
| 3 | GET /api/v1/sync/conflicts | Código de request; falta UI y resolución |

El adaptador se niega a usar HTTP, URLs con path/usuario introducidos, tokens fuera de límites y cuerpo distinto al método. La plataforma valida TLS y hostname, no se cambia el TrustManager ni se siguen redirecciones; timeouts 5s/10s. Las respuestas se acotan a 2 MiB, los POST a 180 KiB y el bearer a 16 KiB. Se devuelven `HttpReply.status` y `body`; **no se confirma ACK ni se modifica cursor ni se finge sincronización**.

La capa Java `NativeHttpTls` es solo adaptador al stack TLS del SO; no contiene los paths del backend. El bearer se maneja temporalmente en memoria Java/Native durante la operación: no se puede prometer borrado de todas las cadenas administradas. No se incluyen tokens, hostnames o secretos fijos en binario.

## Bloqueos de 8.2

1. **OIDC Authorization Code + PKCE real en Android**, browser seguro, token emitido por un IdP y almacenamiento de sesión protegida; el servidor en C++ no debe determinar permisos a partir del cliente.
2. Conectar el motor sync v2 a operaciones UI y documentos cifrados con owner/epoch correctos, validación GCM y ACK durable. No basta con recibir HTTP 200.
3. Transferencia de blobs, token refresh/logout y bloqueo por caducidad, errores 401/409/429, retry jitter, conectividad y tests con backend HTTPS real.
4. Múltiples dispositivos, autorización por propietario, MITM y pruebas de fallos de TLS y tokens en logs. Validar que el origen usado para requests autenticados provenga de una configuración confiable y no de texto libre.
